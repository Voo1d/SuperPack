# SuperPack

Небольшая система учёта склада и производства для примерно 7 сотрудников. Пользовательский интерфейс — Telegram Mini App, адаптированный для телефона и компьютера. `prototype/index.html` и `prototype/app.js` — эталон визуального направления, а не работающий backend.

## Техническое направление

- Frontend: React, TypeScript, Vite.
- Backend: NestJS, TypeScript.
- Хранение: PostgreSQL и Drizzle ORM с миграциями.
- Локальная разработка: Docker Compose для PostgreSQL, команды установки и запуска в README.
- Временный dev-деплой уже настроен отдельно на ARM64 VM и следит за веткой `dev`. Пиши код в рабочей ветке; перенос в `dev` запускает развёртывание, когда таймер активен.
- Контракт dev-деплоя: корневой `Dockerfile` собирает один ARM64-совместимый образ приложения; сервер передаёт `DATABASE_URL` и `PORT`, по умолчанию 8000. Приложение слушает `0.0.0.0:$PORT`, отдаёт React и API с одного origin, отвечает на `/health`, а `npm run migrate` запускает реальные миграции из собранного образа. Сборка не должна требовать токенов или подключения к БД. PostgreSQL уже выделен деплоем и не должен запускаться вторым контейнером из корневого Dockerfile.
- Миграции должны быть совместимы с предыдущим образом приложения. Деплой умеет откатывать образ, но не откатывает схему или данные БД.
- Версии пакетов выбирай из совместимых актуальных релизов и фиксируй lockfile. Не подключай платные внешние сервисы для QR.
- Делай небольшие проверяемые этапы, сообщай файлы, команды запуска, результаты проверок и вопросы, от которых зависит предметная логика.

## Доступ

- Пароля нет. Сервер проверяет подписанные `initData` Telegram Mini App, срок действия и Telegram ID; сам `user.id` из клиентского JSON недостоверен.
- В базе есть сотрудники, роли и признак активного доступа. По умолчанию доступ закрыт; администратор разрешает или отзывает его по Telegram ID.
- Первый администратор задаётся серверной переменной окружения при первоначальной настройке. Запросы к данным и изменениям проверяются сервером.
- Для локальной разработки можно предусмотреть отдельный явно включаемый dev-режим с тестовым пользователем; он должен быть выключен в production и не принимать произвольный ID из клиента.

## Склад

- Четыре категории: «Готовая продукция», «Сырьё», «Запчасти», «Другое».
- Разделяй номенклатуру (товар/материал), партию и движение по партии. У партии есть код, дата поступления или выпуска, единица измерения, исходное количество и текущий остаток. Код партии уникален.
- Поступление, списание, производство и отгрузка должны оставлять историю: кто, когда, сколько, причина/ссылка на операцию. Остатки не должны уходить в минус. Не стирай историю при исправлении: используй корректирующие операции.
- Количества сырья могут быть дробными (кг, м); количество палет, изделий и этикеток — целые неотрицательные или положительные по контексту. Храни значения в единицах измерения без неявного пересчёта.

## Производство и прослеживаемость

- Пользователь отдельно задаёт число палет и изделий в одной палете; итог = произведение этих двух значений. Нужна возможность изменять оба до проведения операции.
- Для выпущенной партии фиксируй факт, план, брак, использованные партии сырья и фактический расход каждой. При проведении списывай сырьё и добавляй готовую продукцию атомарно.
- QR должен разрешаться в сервере в партию или конкретную палету. Не кодируй в QR остаток и другие меняющиеся поля; используй непрогнозируемый публичный идентификатор, не секрет авторизации.

## QR и печать

- В форме этикеток позицию можно заполнить полностью вручную либо выбрать существующую партию со склада/из производства. При выборе партии подставляй её данные и исходное количество QR автоматически; перед экспортом число можно изменить.
- Для готовой продукции исходное число этикеток на палеты = числу палет. Для прочих категорий количество упаковок/этикеток может быть неизвестно: начальное значение 1, которое оператор обязан видеть и менять. Не выдавай количество единиц сырья в кг за число QR.
- Различай режим уникального QR на каждую палету и режим одной ссылки на всю партию с повторяющимися этикетками. Если число уникальных QR больше числа палет, это отдельное предметное решение — не создавай несуществующие палеты молча.
- Экспорт: отдельные PNG и один PDF с несколькими позициями и собственным количеством для каждой (например, 20 для А, 30 для Б, 10 для В). Размер этикетки в мм и поля согласовать перед печатью на XP-365B; печать через PDF/PNG и системный драйвер.
- Ручное создание этикеток для позиции, которой ещё нет в учёте, требует явного решения: только печать или одновременная регистрация партии. Не создавай складской остаток из одной операции печати без подтверждения.

## Качество и границы

- Сначала сквозная вертикальная функция с реальной базой, затем следующие модули; не превращай статический макет в «рабочее приложение» заменой текста или localStorage.
- Сервер валидирует входные данные, применяет роли, сохраняет операции в транзакциях. Добавляй тесты для авторизации и правил движений, а также базовый сценарий приёмки и просмотра партии.
- Не коммить реальные Telegram токены и секреты. Образец переменных — `.env.example`.
