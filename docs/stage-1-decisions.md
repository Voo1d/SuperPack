# Этап 1: принятые решения

Мелкие технические и продуктовые решения, принятые без вопроса к владельцу (см. `TASK-01.md`). Любое можно изменить.

## Доступ
- Проверка `initData` на **каждом** запросе: заголовок `Authorization: tma <initData>`. Сессий и своих токенов нет — отзыв доступа действует мгновенно.
- Подпись: HMAC-SHA256 по схеме Telegram, сравнение через `timingSafeEqual`; `auth_date` старше `INIT_DATA_MAX_AGE_SECONDS` (по умолчанию 24 ч) или из будущего (> 60 с) отклоняется. Telegram ID берётся только из подписанного поля `user` — подменить его, не сломав подпись, нельзя.
- Неизвестный, но подписанный Telegram-пользователь при первом обращении получает запись `pending` (доступ закрыт) и появляется у админа в «Ожидают доступа». Данных он не видит.
- Статусы доступа: `pending` / `active` / `blocked`. Роли: `admin` (всё), `storekeeper` (чтение + приёмка/списание), `production` (чтение; операции производства — этап 2), `viewer` (только чтение).
- `ADMIN_TELEGRAM_IDS` — администраторы из окружения: всегда `active` + `admin`, их нельзя заблокировать или понизить через API (защита от потери доступа). Админ не может менять роль/доступ самому себе.
- Dev-режим: `DEV_AUTH=true` + серверный `DEV_TELEGRAM_ID`. Запрос без `initData` выполняется от этого пользователя; клиент выбрать ID не может. При `NODE_ENV=production` сервер с `DEV_AUTH=true` не стартует. Если `initData` передан, он проверяется как обычно.

## Склад
- Номенклатура (`items`) уникальна по (категория, название без учёта регистра); единица измерения закреплена за позицией. Партия копирует единицу позиции. Приёмка с другой единицей для существующей позиции → `409 ITEM_UNIT_MISMATCH`, а не тихая подмена.
- Единицы: `кг`, `м`, `л` (дробные), `шт.`, `пар`, `упак.` (только целые). Количество — `numeric(18,3)`, по API передаётся строкой/числом без float-арифметики; не более 3 знаков после запятой, не более 12 цифр до неё.
- Код партии: необязателен; если не указан — `FG-`/`RM-`/`SP-`/`OT-` + 4-значный счётчик (пропускает занятые вручную). Хранится в верхнем регистре, уникален без учёта регистра.
- Движения только добавляются (`receipt`, `writeoff`, `correction`), в каждом: кто, когда, сколько, остаток после, причина, ссылка. Остаток меняется атомарным `UPDATE … WHERE остаток + Δ >= 0`, плюс `CHECK` в БД — параллельные списания не уводят остаток в минус. Исправление — отдельное движение `correction`, правки задним числом нет.
- Дата поступления не может быть в будущем (по `APP_TIMEZONE`, по умолчанию `Asia/Tashkent`).
- Готовую продукцию можно принять и вручную (например, начальные остатки); автоматический выпуск из сырья — этап 2. Палеты на этом этапе не моделируются.
- Статус «Мало на складе» из макета не реализован: порогов минимального остатка нет. Вместо него фильтр «Только с остатком / все».

## Инфраструктура
- Два независимых пакета (`server/`, `web/`) со своими lockfile; корневой `package.json` только делегирует команды. В образе `/app` — это собранный `server/` (там же `npm run migrate`) и `public/` с React.
- `GET /health` всегда 200 при живом процессе; поле `db` показывает доступность БД. Миграции — только явной командой `npm run migrate`, при старте сервер их не запускает.
- Миграции обратно совместимы: на этом этапе только создание таблиц.
